# Writing an Architecture Decision Record

How the content of an ADR is written is defined by the ADR rule, which loads when an ADR file is read.
Numbering, file names, links between ADRs, and structural checks are left to the `adrs` CLI, so they are never written by hand.

## 1. Gather the decision

Make sure the conversation or diff at hand can fill every section of [template.md](template.md): the triggering force (Context), what was decided and what was left open (Decision), which alternatives were rejected and why (Alternatives Considered), and what gets worse (Consequences).
Ask the user for anything missing — a fabricated rationale is worse than no ADR, because future readers will trust it.
When part of the decision is still open, ask the user whether to settle it now or to record it under `Not Decided Here`; never write the ADR while a point the Decision depends on is unsettled.

## 2. Locate the ADR directory

```bash
adrs config
```

`adrs` finds the directory from `adrs.toml`, `.adrs.toml`, or `.adr-dir`, and falls back to `doc/adr`.
When ADRs already live in another directory such as `docs/adr` and none of those files exists, prefix every `adrs` command with `ADR_DIRECTORY=<dir>`.
When existing ADRs are not named `NNNN-slug.md`, stop and ask the user, because `adrs` cannot number them.
When no ADR exists yet, run `adrs init`.

## 3. Choose the shape

Keep `Alternatives Considered` only when multiple alternatives were genuinely evaluated — the rejected options are the most valuable part, because they prevent the same evaluation from being redone.
When one clear force drove the decision (e.g. a forced migration), delete the section; empty options are noise.
The heading is `Alternatives Considered`, not `Considered Options`, because `adrs doctor` takes `Considered Options` as a sign of MADR and then demands MADR's sections.

## 4. Create and write the ADR

```bash
adrs new --template ${CLAUDE_SKILL_DIR}/template.md --status Accepted --no-edit "<Decision Title>"
```

When the adr-update skill hands over a supersession, also pass `--supersedes <M>`, which links both ADRs and marks the old one `Superseded`.
Pass `--status Accepted` and `--no-edit` every time, because `adrs` 0.13.0 ignores `default_status` and `no_edit` from the global config and would otherwise write `Proposed` and open an editor.
`adrs new` prints the created path; Read that file, then replace every placeholder in angle brackets.

## 5. Offer a test that guards the decision

When the decision's guarantee can be checked by a test, ask the user whether to add one as the ADR rule describes.
When the repository has no end-to-end test directory, ask where the test should live.
After adding the test, make it fail once on purpose and confirm the failure is reported, because test runners often exclude end-to-end directories and the test would otherwise never run.

## 6. Review before presenting

```bash
adrs doctor --warnings-as-errors
```

Fix every problem reported for the new ADR rather than ignoring the rule.
ADR014 catches only some unfilled placeholders, so also search the new file for a leftover placeholder in angle brackets.
Problems in other ADRs are reported to the user and left as they are, because their bodies are immutable.
Then reread as a reader with no access to this conversation: does the Context alone explain why doing nothing was unacceptable, would any sentence in Decision need rewriting if the implementation changed, is every rationale a "why" rather than a "what", and are the negatives honest?
Fix what fails.
When the ADR directory has a table of contents generated by `adrs generate toc`, regenerate it.
Present the file path and a one-paragraph summary of the recorded decision.
